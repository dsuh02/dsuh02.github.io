01 / work

What I work on

I am on a small team at Persist AI Formulations building a multi-agent platform for pharmaceutical formulation, along with the lab systems around it. The product is closed source, so this is the shape of the work rather than the internals. Happy to go deeper in a conversation.

data platforms

Consolidating a sprawling backend onto Postgres

Led the move from a scattered set of embedded databases and on-disk indexes onto a single PostgreSQL cluster with pgvector. Schema design, migration tooling, and the cutover plan, plus the ongoing work that follows: query performance, indexing strategy, and pooling that holds up under real concurrency.

retrieval

Search that has to earn its cutover

Built the retrieval layer our agents read from: document chunking, embedding pipelines, and two-stage vector search that pairs approximate recall with an exact re-rank. My favorite part of this work is the discipline around it. A retrieval change ships when offline evaluation says it is not a regression, not when it feels better.

pgvectorHNSWIVFFlat embeddingsoffline evals

performance

Making slow things fast, usually by measuring first

A recurring thread in my work: replacing per-row loops with set-based SQL, finding the write path that was the real bottleneck rather than the one I assumed, and choosing index types against the constraints of the machine actually doing the building. The pattern is almost always the same. Profile, get surprised, then fix the thing the profile pointed at.

SQLrecursive CTEsprofiling Postgres internals

architecture

A fleet of services, folded into one

Collapsed a set of HTTP microservices into a single FastAPI service that coordinates an orchestrator and a group of specialist LLM agents over in-process tool calls. Fewer moving parts, no per-request network hops, and a failing request that produces one stack trace instead of a distributed tracing exercise. The tradeoff is real and worth naming: a single process means isolation is now my problem, not the network's.

FastAPIasyncioLLM tool calling multi-provider routing

optimization

An optimizer that has to argue with a chemist

I build the experiment design side of the platform: Gaussian process models over a constrained mixture space, acquisition functions that pick which experiment is worth running next, and convergence tracking across iterations. The engineering problem is less about the math than about trust. A scientist will not run a suggested experiment because a model emitted a number, so most of the work is surfacing uncertainty, the variables that drove a recommendation, and the prior results it leaned on.

Keeping a running system honest

A good share of my week goes to the behavior of software that is already deployed. Health checks that report what is actually true rather than that startup finished. Resource lifetimes that survive long-lived streams and slow upstream calls. And the class of accuracy bug that never shows up in a test suite, only in production logs at two in the afternoon.

full stack and hardware

From the schema to the pipette

I own our lab information management system end to end: the Postgres schema and its append-only history model, the FastAPI endpoints over it, and a React and TypeScript interface for inspecting what is physically where. Underneath it sits the instrument layer, where I write the OPC UA servers, serial bridges, and schedulers that move real hardware.

I also work on our client-facing portal, including the billing path, which is a genuinely interesting corner of engineering. Charging money exactly once, even when the network disagrees with you, turns out to be a transactions-and-idempotency problem rather than a business-logic one.

also on my plate

Multi-tenant authorization

One scope object as the single source of truth for what a caller may read, derived server-side so a client payload can never assert its own ownership. Enforced identically across routes, services, agent tools, and vector search, because an index cannot be an access boundary by itself.

Internal tooling nobody chooses to use

A Flask application our scientists live in, spanning dozens of feature modules: instrument data ingestion from chromatography and spectroscopy runs, plate layout and visualization, and chemical property prediction. Internal tools are judged differently. The bar is never wasting somebody's afternoon.

Tests that refuse to lie

Took a build pipeline from red to green across type checking, both test suites, and linting, with database tests on a least-privilege role that skips safely rather than failing when the runner cannot reach the server. Favorite trick: encoding known-but-unfixed bugs as strict expected failures, so fixing one flips the suite to a hard error instead of quietly passing.

home infrastructure

DigiCalender

active

A touch-wall hub for the house: configurable widgets on a fine-grained grid, with calendars, to-dos, weather, and direct control of the Rokus, Govee plugs, and Samsung TVs on the network. It runs on an always-on Ubuntu box driving a 1920x1080 HDMI touch panel, and comes up on boot with no desktop session.

The constraint that made it interesting: no pip, no build step. Python standard library plus psycopg from apt. The host runs Python 3.14 where wheels are still patchy, and a wall display that will not come up because a dependency failed to compile is worse than a hand-rolled router. So it has a hand-rolled router, an SSE broadcaster, and a minimal RFC 6455 WebSocket client, because the Samsung TVs need one and pip does not exist here.

automotive

Pi dash and reverse camera

An always-on dash system for a Lexus CT200h. A Raspberry Pi 4B drives a 4.3 inch DSI touch display through DRM/KMS with no desktop session, and an overlay service watches the composite capture dongle so that the reverse camera pops on top of the dash UI the moment the feed goes live, then gets out of the way.

Powered off an ACC fuse tap through a buck converter, which means the whole thing has to boot like an appliance every time the key turns.

lab automation

Instrument drivers over OPC UA

The hardware layer of a working wet lab: OPC UA servers exposing object models for spectrometers, pumps, liquid handlers, and plate hotels, plus a robotic arm bridge with streaming motion control and a safety monitor.

Alongside it, Raspberry Pi barcode scanners that post container moves straight into the LIMS, and an LED rack-occupancy display so anyone can see what is loaded from across the room. Failure signaling here is exception-based by policy, because a silent error on a robot arm is far worse than a loud one.

05 / about

The short version

I am a software engineer at Persist AI Formulations in Sacramento. I own our lab information management system end to end and work across the AI platform, which day to day means Postgres schemas, FastAPI services, React interfaces, and a genuinely large amount of time reading production logs. I also run sprint planning and pull request review for the team.

I like the parts of software that touch something real. At work that is instruments and a robot arm in a wet lab. At home it is a panel on the wall that runs the lights. The common thread is that when an abstraction leaks, something physical stops moving, and it turns out that is a very good forcing function for writing honest code.

Computer science at USC, class of 2025, with a California Seal of Biliteracy in French along the way. I speak Korean too. Before all of this I co-founded a hackathon, helped build a solar-powered boat, and wrote for the engineering school's magazine.
